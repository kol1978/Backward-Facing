Почему именно для rhoPimpleCentralFoam это критично
У тебя из лога видно:

max Maf = 0.165 — это малое число Маха
max/min p = 101484 / 98219 — давление почти атмосферное
max/min T = 300.5 / 298.0 — перепад температур маленький
Это значит, что ты решаешь сжимаемую задачу в низкочастотном (low-Mach) режиме. Для плотностных солверов на центральных схемах это самая тяжёлая ситуация:

Почему это происходит
Акустический Courant = 6.6 — слишком высок. Для плотностного солвера на центральных схемах акустический CFL должен быть не больше 1, а у тебя 6.6. kappaFunction с standardMachToAcCourantRatio не справляется с ограничением.
kappa: 0.229 / 0 — коэффициент диссипации падает до нуля в некоторых ячейках. Без диссипации центральная схема становится неустойчивой.
momentumPredictor false — без предиктора скорости давление и скорость не согласованы между outer-итерациями. На второй итерации несогласованность усиливается, энтальпия вылетает.
nOuterCorrectors 3 при nCorrectors 1 — одна коррекция давления на outer-итерацию недостаточна при momentumPredictor false.

Что исправить
В system/fvSolution, секция PIMPLE:
cpp

    nOuterCorrectors            3;      // оставить 3
    nonOrthogonalityThreshold   60;
    skewnessThreshold           0.5;
    fluxScheme                  Kurganov;

    kappaFunction
    {
        type standardMachToAcCourantRatio;

        standardMachToAcCourantRatioCoeffs
        {
        }
    }
}
В system/controlDict:
cpp
adjustTimeStep  yes;
maxCo           0.3;    // было 0.5 — снизить для устойчивости
maxDeltaCo      0.3;    // акустический CFL тоже ограничить
Почему momentumPredictor false — корень проблемы
Без предиктора солвер пропускает этап решения уравнения импульса перед коррекцией давления. В итоге:

Итерация 1: давление считается от «старой» скорости → небольшая ошибка.
Итерация 2: энтальпия пересчитывается от «чуть-чуть неправильного» давления → температура уезжает.
Итерация 3 (не дошла): sqrt от отрицательной T → крах.
С momentumPredictor yes скорость обновляется перед коррекцией давления, и связь «давление → плотность → температура» остаётся согласованной.

Порядок действий
Поставь momentumPredictor yes и nCorrectors 2 в fvSolution.
Снизь maxCo до 0.3 в controlDict.
Запусти с самого начала (startFrom startTime; startTime 0) — накопленная ошибка от предыдущих попыток уже в полях.
Следи за логом: на каждой outer-итерации max/min T должен оставаться в разумных пределах (290–310 K для твоей задачи). Если на итерации 2 температура снова прыгает — значит проблема глубже, нужно смотреть граничные условия.

---------------------Наиболее вероятные причины в твоём стеке (v2312 + icpx + гибридный параллелизм)
Слишком большой шаг по времени / высокий Courant. При Co_max ≈ 6.6 схема не успевает «успеть» за физикой, накапливаются ошибки, и переменные (T, p, rho) уходят в нефизичные диапазоны.
Некорректные граничные условия или начальные поля. Например, профиль скорости/температуры, который не согласуется с физикой задачи, или скачок на границе.
Проблемы с моделью вещества/теплоёмкости. Если cp​(T) или уравнение состояния дают отрицательные величины при выходе T за допустимый диапазон, это быстро приводит к sqrt(negative).
NUMA‑неоднородность и рассинхронизация в гибридном режиме. При неудачной привязке MPI‑процессов и OpenMP‑потоков иногда возникают тонкие эффекты: локальные минимумы/максимумы на границах доменов, которые в сумме дают нефизичные экстремумы.
Оптимизации компилятора (icpx). На агрессивной оптимизации иногда «вылезают» краевые случаи, где при других компиляторах (GCC) ошибка была бы сглажена или не проявлялась.
Ошибки в кастомных полях/модификациях. Если ты менял солвер или добавлял свои поля, там может быть формула, которая при определённых условиях даёт отрицательное число под корнем.

Первичная картина из конфигов
Прежде чем перейти к привязке, фиксирую главное из controlDict и fvSolution — это объясняет, почему численная схема стала уязвима к проблемам привязки.

controlDict: maxCo закомментирован
text
adjustTimeStep  true;
//maxCo           0.7;      ← ЗАКОММЕНТИРОВАНО
maxDeltaT       1;
adjustTimeStep включён, но верхняя граница по Куранту не задана. В rhoPimpleCentralFoam (hybridCentralSolvers) ограничение шага по времени управляется kappaFunction (standardMachToAcCourantRatio), но без maxCo нет жёсткого потолка. Из лога: deltaT вырос с 1e-7 (исходное) до 4.3957e-6 — в 44 раза — и Co_max достиг 6.62. Для Kurganov‑схемы (центрально‑встречный поток, 2‑й порядок) рабочий максимум — порядка 0.5–1.0.

fvSolution: nOuterCorrectors 2, momentumPredictor false
text
nCorrectors      1;
nOuterCorrectors 2;
momentumPredictor false;
fluxScheme       Kurganov;
Две внешние PIMPLE‑итерации, без предиктора скорости. На каждой итерации решается h (энергия) и p (давление) через DILUPBiCGStab с допуском 1e-15. При Co ≈ 6.6 этого недостаточно: первая итерация уже даёт T_max ≈ 307 K, вторая — T_max = 3314 K, T_min = -1691 K. Схема расходится.

fvSchemes: vanLeer + Euler
text
ddtSchemes:     Euler          (1-й порядок по времени)
defaultAdvScheme:  vanLeer     (2-й порядок, TVD)
defaultAdvSchemeV: vanLeerV    (векторный вариант)
Euler по времени + vanLeer по пространству — разумный выбор для сжимаемых течений, но только при Co < 1. При Co > 6 численная диссипация vanLeer не справляется с контролем осцилляций, особенно вблизи границ декомпозиции.

Как неудачная привязка MPI+OpenMP усиливает расходимость
Теперь — главное: почему плохая привязка превращает «высокий, но потенциально survivable Courant» в гарантированный SIGFPE.

1. Глобальный max(Co) при неудачной NUMA‑топологии
В rhoPimpleCentralFoam шаг по времени корректируется через kappaFunction после вычисления локальных чисел Куранта (FaceAcCourant, Maf). Для этого выполняется reduce(max) по всем MPI‑процессам. Если:

MPI‑процессы размещены на разных NUMA‑узлах,
OpenMP‑потоки «гуляют» между ядрами (OMP_PROC_BIND=false или не задан),
I_MPI_PIN_DOMAIN не сконфигурирован,
то MPI_Allreduce для max(Co) может вернуть заниженное значение из‑за задержек синхронизации: процесс на «дальнем» NUMA‑узле ещё не завершил вычисление локального Куранта, а reduce уже прошёл с неполными данными. В результате deltaT остаётся слишком большим — что мы и видим (4.4e-6 вместо требуемых ~6.7e-8 для Co=1).

2. Ghost‑cell exchange при Kurganov‑схеме
fluxScheme Kurganov требует реконструкции потоков на гранях с использованием значений из соседних ячеек. На границах декомпозиции (processor patches) эти значения приходят через MPI‑обмен. Если OpenMP‑потоки «привязаны» не к тому NUMA‑узлу, где живёт буфер приёма:

Кэш‑холодный доступ к ghost‑ячейкам: поток читает данные из памяти удалённого NUMA‑узла (UMA‑штраф 2–4x по латентности).
В PIMPLE‑итерации 1 это даёт запаздывающие значения p и U на границах — flux вычисляется с устаревшими данными.
В PIMPLE‑итерации 2 устаревшие данные накапливаются: h‑уравнение использует искажённый градиент давления → T уходит в нефизичный диапазон → sqrt(T) падает.
3. Floating‑point non‑determinism между NUMA‑узлами
DILUPBiCGStab — би‑сопряжённый градиент со стабилизацией. Редукции внутри итераций (dot products) выполняются через MPI_Allreduce + omp reduction. При плохой привязке:

Порядок суммирования floating‑point чисел различается между запусками и между потоками (floating‑point non‑reproducibility).
tolerance 1e-15 — экстремально жёсткий допуск. При Co ≈ 6.6 и 32 итерациях для p накапливаются ошибки округления порядка 1e-10–1e-8, что достаточно, чтобы сместить решение давления на границе домена.
Различие между PIMPLE‑итерациями 1 и 2 в T (307 → 3314 / -1691) — классический признак того, что небольшая численная разница на границе домена домножается схемой.
4. nOuterCorrectors 2 как усилитель
При nOuterCorrectors 2 вторая итерация использует поля, обновлённые первой. Если в итерации 1 привязка вызвала рассогласование:

Этап	Что происходит при плохой привязке	Следствие
Итерация 1, h	Ghost‑ячейки T на границе декомпозиции — кэш‑холодные, запаздывают	T_max ≈ 307 K (приемлемо)
Итерация 1, p	DILUPBiCGStab с MPI_Allreduce — FP non‑det	p слегка смещён на границе
Итерация 2, h	Использует смещённый grad(p) + запаздывающие ghost T	T_max = 3314 K, T_min = -1691 K → SIGFPE в sqrt
Конкретные рекомендации по привязке
NUMA‑aware MPI+OpenMP конфигурация
Для двух‑узловой NUMA‑системы (предполагая 2 сокета, по N ядер на сокет):

bash
# Пример: 2 MPI процесса, по 6 OpenMP потоков каждый
export OMP_NUM_THREADS=6
export OMP_PROC_BIND=close      # потоки рядом друг с другом
export OMP_PLACES=cores         # привязка к физическим ядрам

export I_MPI_PIN=on
export I_MPI_PIN_DOMAIN=omp     # каждый MPI-процесс получает свой домен
export I_MPI_PIN_CELL=core

mpirun -np 2 ./rhoPimpleCentralFoam -parallel
Ключевые моменты:

I_MPI_PIN_DOMAIN=omp — критично: каждый MPI‑процесс получает свой NUMA‑домен, OpenMP‑потоки не пересекаются с другими процессами.
OMP_PROC_BIND=close — потоки размещаются на соседних ядрах внутри сокета (важно для DILUPBiCGStab, где редукции частые).
OMP_PLACES=cores — жёсткая привязка к физическим ядрам, без миграции.
Проверка правильности привязки
bash
# Проверить фактическое размещение:
mpirun -np 2 -print-topology ./rhoPimpleCentralFoam -parallel

# Или через numactl:
mpirun -np 2 numactl --show ./rhoPimpleCentralFoam -parallel
Если в выводе видно, что процесс 0 и его потоки сидят на node 0, а процесс 1 и его потоки — на node 1, привязка корректна. Если потоки «размазаны» по обоим узлам — привязка сломана.

Что нужно исправить в конфигах (помимо привязки)
Хорошая привязка снижает риск, но первопричина — maxCo закомментирован. Без этого привязка лишь отсрочит падение.

controlDict: раскомментировать maxCo
text
adjustTimeStep  true;
maxCo           0.7;
maxDeltaT       1;
С maxCo 0.7 и kappaFunction standardMachToAcCourantRatio шаг по времени будет ограничен дважды: и по акустическому Куранту (через kappaFunction), и по обычному (maxCo). Это даст deltaT ≈ 1e-7 ... 2e-7 вместо 4.4e-6.

fvSolution:收紧 PIMPLE
text
nOuterCorrectors 1;     // при Co<1 достаточно 1
momentumPredictor true; // включить для устойчивости
momentumPredictor false экономит время, но при высокой сжимаемости и Kurganov‑схеме предиктор даёт лучшую оценку U для корректора давления. При Co > 1 без предиктора расходимость наступает быстрее.

fvSchemes: при запасе по Co — оставить, но рассмотреть fallback
Если после включения maxCo 0.7 расчёт всё ещё нестабилен на границах декомпозиции, можно временно переключить:

text
defaultAdvScheme     upwind;   // вместо vanLeer — для диагностики
defaultAdvSchemeV    upwind;
Upwind — 1‑й порядок, максимально диссипативный. Если с upwind расчёт идёт стабильно, а с vanLeer падает — проблема именно в численной диссипации на границах доменов (усиленной плохой привязкой).

Резюме
Фактор	Влияние	Приоритет исправления
maxCo закомментирован	deltaT растёт без контроля → Co=6.6 → расходимость	Критично
Плохая NUMA‑привязка MPI	Ghost‑обмен запаздывает, max(Co) занижается	Высокий
OpenMP‑потоки без привязки	FP non‑det в DILUPBiCGStab, кэш‑холодные доступы	Высокий

Минимальный набор правок для запуска: раскомментировать maxCo 0.7, включить I_MPI_PIN_DOMAIN=omp + OMP_PROC_BIND=close, поставить momentumPredictor true. Если после этого SIGFPE не повторится — причина была в комбинации высокого Куранта и плохой привязки.

---------------------Возможные причины
С учётом задач (QGD/реакционные солверы, гибридная параллелизация, ICX) наиболее вероятны следующие причины:

Слишком большой шаг по времени или высокий Courant. Max Co = 4.67 — это много для сжимаемых/реакционных солверов. Даже если PIMPLE делает несколько внутренних итераций, при сильных градиентах и реакциях схема может не «вытянуть» такой шаг.
Некорректные граничные условия для T или h. Особенно если используются профили/таблицы (ты ранее спрашивал про fixedProfile): при интерполяции или экстраполяции могут возникать отрицательные значения.
Ошибки в кастомных моделях (QGD, реакции, турбулентность). В форке QGDsolver могут быть формулы, которые при определённых условиях дают отрицательные величины (например, плотность, давление, энтальпия), а затем они попадают под корень.
NUMA‑дисбаланс и разные значения на границах поддоменов. Если на границе MPI‑доменов возникают резкие скачки (из‑за плохой балансировки или привязки процессов к нодам), то градиенты и дивергенции становятся огромными, и схема срывается.
Компиляторные оптимизации ICX. При -fp-model precise ICX может менять порядок операций, и в пограничных случаях это приводит к отрицательным значениям там, где GCC давал «почти ноль».
Проблемы с инициализацией. Если начальное поле T задано некорректно (локальные пики, отрицательные значения), то уже на первых шагах схема может уйти в нефизику.

ICX и strict FP. Флаг -fp-model precise делает вычисления более предсказуемыми, но иногда приводит к тому, что «почти нулевые» отрицательные значения перестают округляться до нуля. Это может быть причиной появления отрицательного аргумента под корнем.
Гибридная параллелизация (MPI+OpenMP). Если внутри солвера используются OpenMP‑циклы, а данные на границах MPI‑доменов несогласованы из‑за NUMA, то локальные градиенты могут быть завышены.
Форк QGDsolver. Поскольку это не апстрим OpenFOAM, любые изменения в моделях могут приводить к нефизичным значениям, особенно при больших градиентах.


------------------Как переключиться с RANS на LES
Замена в одном файле — constant/turbulenceProperties:

------------------Было (RANS, SST k-ω):

simulationType RAS;
RAS
{
    RASModel kOmegaSST;
    turbulence on;
    printCoeffs on;
}

---------------------Стало (LES, WALE):

simulationType LES;
LES
{
    LESModel WALE;
    delta cubeRootVol;
    turbulence on;
    printCoeffs on;

    WALECoeffs
    {
        Cw 0.325;
    }
    cubeRootVolCoeffs
    {
        deltaCoeff 1;
    }
}
