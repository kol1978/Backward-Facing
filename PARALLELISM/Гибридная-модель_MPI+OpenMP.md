# Гибридная модель MPI + OpenMP

## Суть

В чистом MPI у вас 12 процессов, каждый на одном ядре. В гибриде — например,
2 MPI-процесса (по одному на сокет), каждый с 6 OpenMP-потоками:

```
Чистый MPI:          Гибрид MPI+OpenMP:
┌─────┐ ┌─────┐      ┌─────────────────┐  ┌─────────────────┐
│ P0  │ │ P1  │      │ P0 + 6 threads  │  │ P1 + 6 threads  │
│1ядро│ │1ядро│      │ сокет 0 (NUMA 0)│  │ сокет 1 (NUMA 1)│
└─────┘ └─────┘      └─────────────────┘  └─────────────────┘
  ...×12
  12× MPI_Bcast        2× MPI_Bcast
  12× MPI_Send/Recv    2× MPI_Send/Recv
```

## Что выигрываем

- **Меньше MPI-сообщений** — 2 пары вместо ~20: меньше суммарная латентность
  и меньше объём halo-данных (меньше границ разделения сетки).
- **Нет pack/unpack внутри процесса** — OpenMP-потоки разделяют одно
  адресное пространство, поэтому обмен данными между потоками не требует
  буферизации, в отличие от MPI (даже внутри одного узла MPI копирует данные
  между адресными пространствами).
- **Меньше памяти на halo** — дублируются только ячейки на границе между
  2 процессами, а не между 12.

## Что теряем

- **NUMA-локальность сложнее** — MPI-процесс, привязанный к сокету,
  всегда обращается к «своей» памяти. OpenMP-потоки без настройки
  (`OMP_PLACES=cores`, `KMP_AFFINITY=compact`) могут обращаться
  к «чужой» NUMA-ноде — это даёт латентность 2–4× выше.
  Оба подхода (MPI и OpenMP) делят одну физическую ОЗУ,
  но MPI изолирует доступ через отдельные адресные пространства,
  а OpenMP — нет, поэтому управление NUMA ложится на программиста.
- **Накладные расходы OpenMP** — fork/join и барьеры на каждом параллельном
  цикле. Для коротких циклов overhead может съесть весь выигрыш.
- **MPI_THREAD_FUNNELED** — типичный уровень для OpenFOAM: MPI-вызовы
  идут только из главного потока, OpenMP-параллелизм — в вычислительных
  циклах. Это не ограничение, а архитектурное решение, но оно означает,
 что MPI-коммуникации нельзя распараллелить между потоками.
